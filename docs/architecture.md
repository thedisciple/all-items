# Architecture

All Items is a single Next.js App Router application. Server-rendered UI and server actions call the item service in `src/items`; that service validates inputs with Zod and uses the local libSQL SQLite client. Ordered SQL migration files live in `src/db/migrations`. The runner applies each migration and records it in the same write transaction. App startup may apply pending migrations; `npm run build` and tests do not open the configured user database.

The schema contains one local workspace, UUID item identities, deterministic per-workspace inventory numbers, item details, locations, stock entries, private media metadata, collections, and item-collection memberships. M1 backfills numbers by creation timestamp and UUID, retaining existing UUIDs, names, models, and timestamps. M2B adds collections through migration 0004 without updating existing item, stock, location, or media rows. Each collection belongs to a workspace; membership constraints and database triggers prevent duplicate or cross-workspace membership. Deleting a collection cascades only to membership rows. Existing items start with quantity one and unique tracking mode. New unique items also start at one; bulk and consumable items start at zero. A unique item must have a total quantity of exactly one. Stock quantities are nonnegative.

The database and media live under `%LOCALAPPDATA%\AllItems` on Windows and `~/.all-items` elsewhere by default (or `ALL_ITEMS_DATA_DIR`), outside the repository. Builds and tests use isolated databases and do not open configured user data. The web process binds to `127.0.0.1` by default. Sale intent and price are local private metadata only.

M2A accepts JPEG, PNG, and WebP input up to 10 MiB, 12,000 pixels per side, and 40 megapixels. Sharp decodes and auto-orients input, resizes without upscaling, and writes metadata-stripped WebP image and thumbnail files. The uploaded original is not retained. Files live under `media/items/<item UUID>/<media UUID>.webp`; those names are generated by the server. SQLite stores paths relative to that controlled root. Media routes validate item and media UUIDs, require a matching primary media row, recompute paths from UUIDs, and return private non-cacheable responses. M2B uses a browser source chooser for camera or file. Camera requests video only after an explicit click; access depends on secure-context rules and browser/device permission. File selection remains available. New item creation waits for the Add Item action; replacement submits after a file or capture is selected, keeps the old media until metadata swaps, and allows retry after failure. The preview uses a temporary object URL that is revoked on replacement/cancel/unmount. Current processing remains server-side; no client compression, upload percentage, resumable queue, or cancellation after submission is implemented. SQLite and filesystem changes are not one atomic transaction. If post-delete file cleanup fails, the database record is already removed and the controlled route cannot serve that orphaned file. This unauthenticated version is for loopback use only and does not provide multi-user access control.

Keep domain behavior outside React components and evolve schema through additive migrations. Collections are a distinct logical view; categories and physical locations retain separate meanings. Item membership is many-to-many and never duplicates the item. Future authentication and workspace ownership can build on the stable UUIDs. M2B does not implement AI identification, sync, multi-user support, public endpoints, achievements, analytics, or marketplace flows.
