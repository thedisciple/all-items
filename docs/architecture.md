# Architecture

## M3.4 ordered media and exact prices

Migration 0011 adds deterministic contiguous photo order and a unique (item, order) index without changing valid legacy IDs, paths or primary choices. Gallery writes verify explicit inventory/item ownership and exactly one primary for non-empty lists inside the write transaction. Reordering never deletes assets. Replacement stages a new media UUID, transfers the target position/primary and explicit cover references transactionally, then cleans the old unreferenced files. Deletion promotes the first surviving ordered photo and deliberately resets covers referencing the removed UUID. Controlled routes now serve any owned gallery media ID, including its stripped editable source, with generated-path and private-path checks. Legacy sources remain optional.

Migration 0012 adds asking_price_exponent default 2, preserving the meaning of every historical amount/code. New amounts use a pinned, verified ISO table rather than runtime Intl display defaults. Exact decimal-string arithmetic avoids binary rounding; unchanged currencies retain their stored exponent when editing. ZIP revision 6 includes ordered arrays, primary UUID and price exponent. Tested revision 2–5 adapters preserve their old precision and presentation policy. Browser sidebar/locale/draft preferences remain excluded from archives.

New photo-only unnamed records store an empty name; rendering and localized fallback search are separate from stored literal titles. The sidebar preference is a first-party browser cookie used in server rendering, not an inventory setting or authorization. See [design decisions](product/m3-4-design.md) and [validation](architecture/m3-4-validation.md).


## M3.3B local recovery and presentation

The Add Item workflow stores versioned, inventory-scoped drafts in browser IndexedDB. Records contain only form fields, stock, selected and source photo Blobs, crop state and pending crop input. Reads require an explicit Restore or Discard choice. Each read-write transaction compares a revision so a second tab cannot silently overwrite a newer record. Drafts expire after 30 days, have bounded photo sizes and entry counts, and storage failures leave the in-memory form available. IndexedDB commit is asynchronous: a crash before a write commits can lose the latest changes. Draft Blobs may temporarily contain the original file's metadata; they never enter portable archives or leave the device.

Migration `0010` adds workspace-local default sorting and custom-category emoji without altering existing items or assignments. ZIP revision 5 carries only that allowlisted presentation and sorting state; revisions 2–4 restore with defaults. Locale and the last selected inventory remain browser preferences. New photo-first item fields, category presentation, stock and the media database reference commit together after private files are staged; rollback removes staged files when possible. SQLite and the filesystem are not an atomic unit, so an abrupt process interruption may leave unreferenced staged files.

## M3.3A inventory boundaries

The current implementation uses explicit InventoryContext values throughout item, stock, collection, media, category, CSV and ZIP services. Canonical pages and controlled media/API routes live under `/inventories/<UUID>`. Forms carry the route inventory ID; a cookie only chooses the landing preference. Legacy detail and media routes deliberately target the original inventory and never infer an edit target from the preference. New installations seed the original workspace once in migration 0008; reads and startup after an explicit final deletion do not recreate it. Installation-wide create/list operations remain separate from inventory-scoped domain services.

Migration 0008_inventory_boundaries adds immutable ownership and human-number triggers, a monotonic sequence guard, stock-location and cover ownership checks, and default-cover cleanup when selected media or membership is removed. Human numbers are scoped per inventory, immutable, and never automatically reused after deletion. Existing UUIDs, rows and private paths are preserved. File cleanup receives the operation inventory and rejects live assets owned elsewhere. ZIP revision 4 permits arbitrary inventory UUIDs; revisions 2/3 retain their original single-inventory contract. Every export snapshot query joins its selected parent inventory, checks generated media identities, and runs the read-only archive verifier before returning bytes.

The following sections retain historical milestone details. Checkpoint C adds full ID-remapped import into a new inventory, a transaction commit marker, generated private destinations, process-aware operation serialization, retained source archives/journals and startup recovery. Checkpoint D adds scoped deletion with a verified full-installation SQLite/media backup, typed confirmation for populated inventories, rechecked snapshot/media hashes, transactional child/parent deletion and foreign-key validation. A durable deletion journal coordinates post-commit generated-path cleanup; startup removes only unreferenced files for a target that no longer exists. A failed transaction preserves the inventory; a failed cleanup preserves the backup/journal. Deleting the last inventory does not rerun the original workspace seed.


## M3.2-R1 category and editing transition

Migration 0007 adds `item_categories(item_id, category)` with a unique pair and a category/item index. A category value is either a stable global system key or an exact custom label; there is no duplicate per-workspace taxonomy. Existing recognized English/Russian aliases are backfilled to keys, unknown values remain custom, and all original item rows remain intact. `items.category` is an immutable legacy snapshot. Reads, search, filters, editing, CSV and current archives use the relation exclusively. The single-category URL filter uses EXISTS, so multiple assignments never duplicate an item; category, status, search and collection scope combine with AND.

One domain write transaction validates metadata, the intended inventory type and stock together, resolves workspace-owned locations, replaces category associations, reconciles stock, and commits once. Unchanged stock rows keep their IDs and timestamps. Empty whitespace/zero draft rows are omitted; a legitimate positive unlocated quantity is retained. Single-item conversion requires one meaningful row with quantity one and rejects incompatible drafts. Photos retain their separate persisted replacement lifecycle.

The explicit migration/startup command creates a SQLite VACUUM INTO snapshot and verified media copy under the private data directory before pending migrations on an existing database. It checks SQLite integrity, foreign keys, referenced media presence and copied file SHA-256 hashes. A failed backup stops migration. Keep the app stopped during migration so database and media remain consistent. Tests/builds use isolated data and never invoke configured-data migration. Revision 3 category arrays have a tested revision 2 single-category transition importer; revision 1 remains unsupported.

All Items is a single Next.js App Router application. Server-rendered UI and server actions call the item service in `src/items`; that service validates inputs with Zod and uses the local libSQL SQLite client. Ordered SQL migration files live in `src/db/migrations`. The runner applies each migration and records it in the same write transaction. App startup may apply pending migrations; `npm run build` and tests do not open the configured user database.

Historically the foundation schema began with one local workspace, UUID item identities, deterministic per-workspace inventory numbers, item details, locations, stock entries, private media metadata, collections, and item-collection memberships. M1 backfills numbers by creation timestamp and UUID, retaining existing UUIDs, names, models, and timestamps. M2B adds collections through migration 0004 without updating existing item, stock, location, or media rows. M2C introduces categories without a database migration: new selections store stable keys, while existing free-text values remain untouched and exact legacy aliases map only at display/filter time. Each collection belongs to a workspace; membership constraints and database triggers prevent duplicate or cross-workspace membership. Deleting a collection cascades only to membership rows. Existing items start with quantity one and unique tracking mode. New unique items also start at one; bulk and consumable items start at zero. A unique item must have a total quantity of exactly one. Stock quantities are nonnegative.

The database and media live under `%LOCALAPPDATA%\AllItems` on Windows and `~/.all-items` elsewhere by default (or `ALL_ITEMS_DATA_DIR`), outside the repository. Builds and tests use isolated databases and do not open configured user data. The web process binds to `127.0.0.1` by default. Sale intent and price are local private metadata only.

M2A accepts JPEG, PNG, and WebP input up to 10 MiB, 12,000 pixels per side, and 40 megapixels. Sharp decodes and auto-orients input, resizes without upscaling, and writes metadata-stripped WebP image and thumbnail files. The uploaded original is not retained. Files live under `media/items/<item UUID>/<media UUID>.webp`; those names are generated by the server. SQLite stores paths relative to that controlled root. Media routes validate item and media UUIDs, require a matching primary media row, recompute paths from UUIDs, and return private non-cacheable responses. M2C uses a browser crop dialog before submission/replacement and a single detail-page viewer. Browser-decoded images apply EXIF orientation; Canvas output is then normalized by Sharp. Cropping an existing photo edits its saved normalized derivative because the original uncropped source is not retained. The old media row/file remains until replacement has persisted, and unique media IDs prevent stale-cache reuse. The preview uses a temporary object URL that is revoked on replacement/cancel/unmount. Current processing remains server-side after upload; no client compression, upload percentage, resumable queue, or cancellation after submission is implemented. SQLite and filesystem changes are not one atomic transaction. If post-delete file cleanup fails, the database record is already removed and the controlled route cannot serve that orphaned file. This unauthenticated version is for loopback use only and does not provide multi-user access control.

The App Router locale is selected from an explicit first-party cookie, then a supported browser language, then Russian. Complete Russian, English, Ukrainian, Serbian Latin, and Simplified Chinese dictionaries are bundled locally and typed; user-entered content is never auto-translated. Counts, dates, and numbers use Intl locale data. Server-to-client item, stock, and collection values use explicit primitive DTO projections. Keep domain behavior outside React components and evolve schema through additive migrations. Collections are a distinct logical view; categories and physical locations retain separate meanings. Item membership is many-to-many and never duplicates the item. Future authentication and workspace ownership can build on the stable UUIDs. This milestone does not implement AI identification, sync, multi-user support, public endpoints, achievements, analytics, or marketplace flows.

M3.2 provides a local Data page for full-fidelity revision 3 ZIP export, empty-workspace import, and separate spreadsheet CSV. The ZIP uses readable, collision-safe paths for presentation, a versioned JSON interchange payload for stable identities, bounded media entries, manifest SHA-256 checksums, and a read-only verifier. It preserves all supported item, stock, location, collection, membership, cover, private sale, and media metadata without exporting raw SQLite. Metadata is captured in a short SQLite read transaction; private files are then resolved from identifier-derived paths and checked for missing data and symbolic links. Filesystem and SQLite are not atomic together, so export aborts if referenced media changed or disappeared. The route uses no-store/private download headers and never uploads externally. See [archive format](architecture/archive-format.md).

Import validates revision, ZIP structure, resource bounds, paths, checksums, typed JSON, relationships, and decoded WebP media before preview. Confirmed import revalidates, stages media in the configured data directory, checks staged hashes, promotes media to generated identifier paths while a SQLite write transaction is open, inserts records, checks foreign keys, and commits. Failure rolls back visible rows and removes promoted files; a staging journal supports cleanup on a later attempt after interruption. The target must have no inventory data, so there is no merge or replacement. SQLite and filesystem operations are not jointly atomic: a sudden power loss or damaged disk may require recovery from the retained source archive. Revision 2 remains importable through a tested single-category adapter; revision 1 is unsupported.

The [multiple-inventory ADR](architecture/adr-multiple-inventories.md) governs the implemented M3.3A scoping, ID remapping, isolation and recovery boundaries; account authorization remains future work.

## Planned portability and integration boundaries

M3.2-R1 implements revision 3 ZIP export and empty-workspace restore, retaining revision 2 restoration. A future populated-workspace merge or replacement needs a separate conflict model, verified backup, and recovery path. A public format compatibility policy, optional encryption, and styled XLSX export are later enhancements. Import tests use isolated data and never implicitly migrate or overwrite configured user data.

Keep future integrations behind narrow interfaces: archive export/import, media/blob storage, optional backup destinations, AI providers, external authentication identity providers, and MCP/API access. Local storage remains the default. Potential implementations include Ollama/OpenAI providers, S3-compatible or WebDAV/Nextcloud storage, and user-initiated Telegram sharing. None is implemented here; Telegram must not become the primary database or file backend.

For a possible M3.5 pilot of 5–10 invited testers, access across the network requires production-mode hosting, authenticated HTTPS, secure sessions, explicit workspace authorization in every domain and media route, CSRF/origin protections, rate limits, upload limits, security headers, and tested backup/recovery. Owner data migration must be staged and recoverable. Keep dev endpoints private. Optional Telegram Login/OIDC can map an external identity to an All Items account only; it does not authorize Telegram chats or file access. Do not request MTProto session credentials. Telegram's [Bot Developer Terms](https://telegram.org/tos/bot-developers) restrict standalone cloud-storage use and do not guarantee cloud-storage data availability or integrity, so Bot Platform storage is not an archive or backup foundation. Login integration should follow Telegram's [Login documentation](https://core.telegram.org/bots/telegram-login). A public or multi-user deployment is not implemented by this milestone.

## Remaining advanced media work

Ordered private galleries, primary promotion, per-image edits and revision 6 media-list restoration are implemented in M3.4. Batch intake/queues, annotations, undo history, AI-assisted selection, public sharing and cloud storage remain future work. SQLite/filesystem transactions still cannot be jointly atomic; abrupt interruption may leave unreferenced staged photo files. Import/deletion retain their existing journals and verified recovery sources.
