# Architecture

## M3.2-R1 category and editing transition

Migration 0007 adds `item_categories(item_id, category)` with a unique pair and a category/item index. A category value is either a stable global system key or an exact custom label; there is no duplicate per-workspace taxonomy. Existing recognized English/Russian aliases are backfilled to keys, unknown values remain custom, and all original item rows remain intact. `items.category` is an immutable legacy snapshot. Reads, search, filters, editing, CSV and current archives use the relation exclusively. The single-category URL filter uses EXISTS, so multiple assignments never duplicate an item; category, status, search and collection scope combine with AND.

One domain write transaction validates metadata, the intended inventory type and stock together, resolves workspace-owned locations, replaces category associations, reconciles stock, and commits once. Unchanged stock rows keep their IDs and timestamps. Empty whitespace/zero draft rows are omitted; a legitimate positive unlocated quantity is retained. Single-item conversion requires one meaningful row with quantity one and rejects incompatible drafts. Photos retain their separate persisted replacement lifecycle.

The explicit migration/startup command creates a SQLite VACUUM INTO snapshot and verified media copy under the private data directory before pending migrations on an existing database. It checks SQLite integrity, foreign keys, referenced media presence and copied file SHA-256 hashes. A failed backup stops migration. Keep the app stopped during migration so database and media remain consistent. Tests/builds use isolated data and never invoke configured-data migration. Revision 3 category arrays have a tested revision 2 single-category transition importer; revision 1 remains unsupported.

All Items is a single Next.js App Router application. Server-rendered UI and server actions call the item service in `src/items`; that service validates inputs with Zod and uses the local libSQL SQLite client. Ordered SQL migration files live in `src/db/migrations`. The runner applies each migration and records it in the same write transaction. App startup may apply pending migrations; `npm run build` and tests do not open the configured user database.

The schema contains one local workspace, UUID item identities, deterministic per-workspace inventory numbers, item details, locations, stock entries, private media metadata, collections, and item-collection memberships. M1 backfills numbers by creation timestamp and UUID, retaining existing UUIDs, names, models, and timestamps. M2B adds collections through migration 0004 without updating existing item, stock, location, or media rows. M2C introduces categories without a database migration: new selections store stable keys, while existing free-text values remain untouched and exact legacy aliases map only at display/filter time. Each collection belongs to a workspace; membership constraints and database triggers prevent duplicate or cross-workspace membership. Deleting a collection cascades only to membership rows. Existing items start with quantity one and unique tracking mode. New unique items also start at one; bulk and consumable items start at zero. A unique item must have a total quantity of exactly one. Stock quantities are nonnegative.

The database and media live under `%LOCALAPPDATA%\AllItems` on Windows and `~/.all-items` elsewhere by default (or `ALL_ITEMS_DATA_DIR`), outside the repository. Builds and tests use isolated databases and do not open configured user data. The web process binds to `127.0.0.1` by default. Sale intent and price are local private metadata only.

M2A accepts JPEG, PNG, and WebP input up to 10 MiB, 12,000 pixels per side, and 40 megapixels. Sharp decodes and auto-orients input, resizes without upscaling, and writes metadata-stripped WebP image and thumbnail files. The uploaded original is not retained. Files live under `media/items/<item UUID>/<media UUID>.webp`; those names are generated by the server. SQLite stores paths relative to that controlled root. Media routes validate item and media UUIDs, require a matching primary media row, recompute paths from UUIDs, and return private non-cacheable responses. M2C uses a browser crop dialog before submission/replacement and a single detail-page viewer. Browser-decoded images apply EXIF orientation; Canvas output is then normalized by Sharp. Cropping an existing photo edits its saved normalized derivative because the original uncropped source is not retained. The old media row/file remains until replacement has persisted, and unique media IDs prevent stale-cache reuse. The preview uses a temporary object URL that is revoked on replacement/cancel/unmount. Current processing remains server-side after upload; no client compression, upload percentage, resumable queue, or cancellation after submission is implemented. SQLite and filesystem changes are not one atomic transaction. If post-delete file cleanup fails, the database record is already removed and the controlled route cannot serve that orphaned file. This unauthenticated version is for loopback use only and does not provide multi-user access control.

The App Router locale is selected from an explicit first-party cookie, then a supported browser language, then Russian. Complete Russian, English, Ukrainian, Serbian Latin, and Simplified Chinese dictionaries are bundled locally and typed; user-entered content is never auto-translated. Counts, dates, and numbers use Intl locale data. Server-to-client item, stock, and collection values use explicit primitive DTO projections. Keep domain behavior outside React components and evolve schema through additive migrations. Collections are a distinct logical view; categories and physical locations retain separate meanings. Item membership is many-to-many and never duplicates the item. Future authentication and workspace ownership can build on the stable UUIDs. This milestone does not implement AI identification, sync, multi-user support, public endpoints, achievements, analytics, or marketplace flows.

M3.2 provides a local Data page for full-fidelity revision 2 ZIP export, empty-workspace import, and separate spreadsheet CSV. The ZIP uses readable, collision-safe paths for presentation, a versioned JSON interchange payload for stable identities, bounded media entries, manifest SHA-256 checksums, and a read-only verifier. It preserves all supported item, stock, location, collection, membership, cover, private sale, and media metadata without exporting raw SQLite. Metadata is captured in a short SQLite read transaction; private files are then resolved from identifier-derived paths and checked for missing data and symbolic links. Filesystem and SQLite are not atomic together, so export aborts if referenced media changed or disappeared. The route uses no-store/private download headers and never uploads externally. See [archive format](architecture/archive-format.md).

Import validates revision, ZIP structure, resource bounds, paths, checksums, typed JSON, relationships, and decoded WebP media before preview. Confirmed import revalidates, stages media in the configured data directory, checks staged hashes, promotes media to generated identifier paths while a SQLite write transaction is open, inserts records, checks foreign keys, and commits. Failure rolls back visible rows and removes promoted files; a staging journal supports cleanup on a later attempt after interruption. The target must have no inventory data, so there is no merge or replacement. SQLite and filesystem operations are not jointly atomic: a sudden power loss or damaged disk may require recovery from the retained source archive. Earlier experimental revision 1 archives are unsupported for import.

## Planned portability and integration boundaries

M3.2 implements revision 2 ZIP export and empty-workspace restore. A future populated-workspace merge or replacement needs a separate conflict model, verified backup, and recovery path. A public format compatibility policy, optional encryption, and styled XLSX export are later enhancements. Import tests use isolated data and never implicitly migrate or overwrite configured user data.

Keep future integrations behind narrow interfaces: archive export/import, media/blob storage, optional backup destinations, AI providers, external authentication identity providers, and MCP/API access. Local storage remains the default. Potential implementations include Ollama/OpenAI providers, S3-compatible or WebDAV/Nextcloud storage, and user-initiated Telegram sharing. None is implemented here; Telegram must not become the primary database or file backend.

For a possible M3.5 pilot of 5–10 invited testers, access across the network requires production-mode hosting, authenticated HTTPS, secure sessions, explicit workspace authorization in every domain and media route, CSRF/origin protections, rate limits, upload limits, security headers, and tested backup/recovery. Owner data migration must be staged and recoverable. Keep dev endpoints private. Optional Telegram Login/OIDC can map an external identity to an All Items account only; it does not authorize Telegram chats or file access. Do not request MTProto session credentials. Telegram's [Bot Developer Terms](https://telegram.org/tos/bot-developers) restrict standalone cloud-storage use and do not guarantee cloud-storage data availability or integrity, so Bot Platform storage is not an archive or backup foundation. Login integration should follow Telegram's [Login documentation](https://core.telegram.org/bots/telegram-login). A public or multi-user deployment is not implemented by this milestone.

## Future multi-photo migration path (planned; not implemented)

`media_assets` already gives each photo a stable UUID, an owning `item_id`, private source and derivative paths, crop metadata, and `is_primary`. A partial unique index currently permits at most one primary photo per item. The present service and media route deliberately expose the primary image only; do not infer that multiple-photo UI is supported.

Plan the next media milestone as an additive migration: add a non-negative `display_order` to each media row, backfill deterministic per-item ordering using current creation time and media UUID, retain every existing ID and private path, and leave the current primary row unchanged. Keep the partial unique primary index. The media service must transactionally maintain one primary whenever an item has media; SQL uniqueness can enforce at most one, while the service transaction ensures at least one. Deleting a primary should promote the next ordered image in the same transaction, with a user-selected replacement supported by the same operation. Reordering changes only order values.

Build a gallery against media IDs, never path values from clients. Every image keeps its own normalized editable source, crop operation, display derivative, and thumbnail. Item list cards continue to use the primary. Collection covers that reference item media must continue to validate membership and a live media ID; deleting the referenced image should resolve to a safe default or an explicit replacement policy without deleting the item. Archive manifests must encode `mediaAssets: []` per item, each record carrying stable ID, primary flag, display order, crop data, and relative asset references with checksums. Import maps these lists and references together. Validate this plan with migration tests on isolated copies and backup/restore before touching configured user data.
