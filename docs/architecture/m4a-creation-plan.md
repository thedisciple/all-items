# M4A creation and retry plan

Status: checkpoint C implementation; final verification is recorded in [M4A validation](m4a-validation.md). The supplied brief permits staging plus one final commit. Preserve ZIP revision 6 and legacy 2–5 importers. No accounts, LAN, AI or later milestone is authorized here.

## Alternatives and decision

A single multipart create action bounded to about 20 MiB would fit the current 22 MiB body limit, but substantially restrict ten ordinary camera sources once derivatives are included. Raising the body limit to accommodate ten maximum-sized pairs would increase buffering and memory pressure. Prefer bounded sequential per-photo staging, followed by a small final command. Staging contains only metadata-stripped normalized source/display/thumbnail files outside Git. It creates no hidden item. Existing Sharp per-file 10 MiB, 12,000-side and 40MP checks remain authoritative; validate source size before allocation. Process one image at a time using the existing process-aware inventory-operation lock.

Implemented separate budgets: 10 new photos; 64 MiB of distinct input photo Blobs per draft/creation; 128 MiB across browser drafts (existing global policy); 64 MiB normalized staging per operation; bounded aggregate server staging (256 MiB) and 24-hour expiry with startup/next-operation cleanup. Each request still fits 22 MiB. Count source/display aliases once when they are the same Blob; do not count filesystem derivatives as photos. Validate input types, dimensions and pixels before browser preview decode; use sequential small bitmap thumbnails, not ten decoded full-resolution preview images. The resource regression suite checks each server staging budget independently.

## Durable retry identity (audit addition)

A lost final acknowledgement must not duplicate an item or consume a second human number. Use an additive item-write receipt table in the same transaction as the write. Scope operation UUIDs by inventory; bind kind and a canonical SHA-256 request fingerprint. Keep tombstones if a completed item/photo is later deleted so a stale retry cannot recreate it. Receipts and browser operation IDs are installation/recovery state and never portable inventory fields. Preserve original rows and media through a verified private pre-migration snapshot and after-comparison.

The same ambiguity exists for existing-gallery photo additions/replacements: a transport failure after commit can otherwise duplicate an addition or retry a removed replacement ID. Reuse the receipt mechanism for those non-idempotent media writes; primary/order changes are naturally repeatable. Add a stable operation UUID to each accepted selection, retain it for retry, until acknowledgement or explicit cancellation. Resolve a completed receipt before cap checks or cleanup, including inside the transaction for concurrent retries. A request with changed content but a completed key must be rejected, preserving its draft and offering deliberate recovery.

## Private staging and finalization

- Validate inventory context and UUID identifiers at every boundary. Directory names and destinations are generated from validated server identities; accept no path from a client. Stages need no public media/download route because the browser retains its own Blobs.
- Begin/prepare an operation with its desired client-photo IDs; prune removed draft-photo stages, retain unchanged ones, and reserve a fresh server item UUID without inserting a row. Stage one photo per request. Server records actual input digests, crop metadata, normalized file hashes/sizes and server media UUIDs. Repeated identical stage requests reuse the verified stage. A new version persists before an old stage is removed.
- Browser computes file digests sequentially (cached by File identity), freezes one final metadata/stock/category/order/primary command and awaits a committed local draft write before submission when storage is available. A denied/quota/conflicting browser store stays an explicit limitation, not an invented crash guarantee.
- Finalize under the operation lock: verify canonical command hash, scoped tokens, actual normalized bytes, count/order/primary and budgets. Record a durable promotion journal before generated exclusive file copies. Preflight collisions, reject links and verify hashes. Do not delete any pre-existing destination on an exclusive-write failure.
- In one SQLite transaction, check receipt before allocating a number, then insert item, stock, categories, all media/order/primary and receipt. No partial visible item is committed if the second image fails. Fields remain validated by the existing domain schemas.
- Acknowledge and clear the matching browser revision only after verified completion. On ambiguous commit, inspect the receipt before touching promoted files. On ordinary failure, remove only generated unreferenced promoted files; retain prepared stages for retry. Startup recovery uses receipt/reference checks, never guesses from browser cookies, and never restores deliberately deleted photos or recreates a deleted inventory. Expired stage copies can be removed; corrupt journals fail closed. SQLite and files are not one atomic storage device.

## Multi-photo browser state

Use the same GalleryRail and PhotoViewer navigation as saved galleries. Multiple file input and sequential camera capture append to a bounded local array. Selected viewing, primary identity and committed local order remain separate. Each photo retains accepted derivative, original/source, pending replacement and accepted/pending crop coordinates. Adding files displays bounded thumbnails immediately; editing one photo never rewrites siblings. Preserve a selected derivative until new crop encoding succeeds; Cancel restores it. Object URLs and camera tracks have explicit cleanup.

Upgrade records to draft shape version 2 in memory without an automatic write. A legacy single-photo record retains its revision/CAS identity; derive stable initial photo/operation IDs from that UUID so two tabs read the same legacy identity. Persist ordered photos, primary, visible selection, current crop input/geometry and operation identity, with Blob and aggregate validation. Keep unknown/corrupt drafts intact instead of silently replacing them. Save succeeds once, clears only its own committed revision and never exports draft state.

## Required evidence

Three distinct crops/primary/order, ten-photo intake and eleventh rejection; repeat camera mocks and denied permission; full multi-photo restart restore and legacy record recovery; denied/quota/cross-tab CAS; stale/foreign stage tokens; failed normalization, promotion, transaction and interrupted network/commit acknowledgement; concurrent identical/different receipt requests and no extra human number; metadata-free normalized files and unchanged sibling/owner media; ZIP6 duplicate import and legacy 2–5 adapters, including >10 persisted galleries. Report physical devices and storage-damage limits honestly.

## Concrete implementation constraints established before C

These decisions were recorded before implementation and are now reflected in the code:

- Bind the whole frozen command (raw validated fields, stock/category presentation, ordered photo UUIDs, source/display SHA-256/size/name/type, crop and primary UUID) through canonical sorted-key JSON and SHA-256. Preserve array order. Share the command schema/serialization without importing database or React code into the browser.
- Send that small command with each one-photo stage request. This lets a completed receipt be resolved before normalization or missing-stage reads, even after reload/expiry. Verify actual uploaded hashes, sizes and normalized checksums; never trust a client digest alone. Finalization repeats command validation and fingerprint comparison. A changed command may replace only an uncommitted preparation; a completed key rejects changed content and offers its existing item plus a deliberate new-operation choice.
- Keep the action body limit at 22 MiB: one request contains at most a 10 MiB display and 10 MiB source. Distinct source/display aliases can upload once. Ten is a photo count, not a byte allowance. Stage only normalized assets. Add a global maximum of 64 pending operations alongside the proposed 256 MiB budget and 24-hour expiry, so tiny operations cannot grow metadata without bound. Normalized assets must also fit the existing 32 MiB ZIP-entry limit.
- Prepare/normalize sequentially under the existing process-aware operation lock. Final promotion uses server-generated item/media UUIDs, exclusive destinations and a durable journal before a short database write. Resolve receipt/reference state before cleanup on every failure and startup recovery. Track files actually created; an exclusive-copy collision must never delete a pre-existing file. Recover or fail closed before replacing a journal.
- The additive receipt table covers create/add/replace. Insert the receipt inside the same write transaction, before returning acknowledgement. Check it before cap checks/number allocation and again in the transaction. Nullable result FKs preserve tombstones after deliberate deletion; inventory deletion cascades receipts. No portable revision is needed. Persist the operation UUID in the browser draft before the first server write when storage is available.
- For the browser shape upgrade, a legacy revision UUID can supply both initial photo and operation identities in their separate namespaces. Retain its original revision/updatedAt and do not automatically rewrite it. Reconstruct aliased Files once per stored Blob identity so source/display aliases do not unexpectedly double the restored byte budget. Preserve corrupt/unknown records and fail local writes rather than overwriting them.
- Append a bounded batch only after slot/type/byte/dimension validation. Generate small thumbnails sequentially and close bitmap resources; keep only the selected full preview/crop decoded. A single-file intake may open the existing crop flow; a batch must not force ten crop confirmations. Keep acquisition and selected-photo crop controls distinct, with the shared rail/viewer/primary pattern.
- Persist pending crop geometry separately from the accepted crop/derivative. Debounce routine local writes to avoid repeatedly serializing every Blob during pointer movement, but flush/await the latest snapshot before submission. Explicit restore tokens change only on selection or restore, not on each geometry update. Cancel retains the prior accepted derivative. Stop camera tracks when its source dialog or the containing Add Item dialog closes.
- Existing-gallery media retries also need stable accepted-selection operation UUIDs. Update the hidden operation identity synchronously before automatic submission, retain it through transport failures, and generate a new identity only after acknowledgement or explicit cancellation. Add actual lost-postcommit-response tests, beyond B's pre-server aborted request.

Media retry refinement during implementation: an unacknowledged add/replace retains one operation UUID even if its draft is corrected. A completed key with changed bytes is rejected while retaining File/source; explicit Cancel selection ends that attempt and refreshes the confirmed gallery. This is safer than automatically generating a new key for a changed crop after a lost acknowledgement, which could silently duplicate an already-committed addition. The mounted client action controller attaches the stable UUID before server dispatch.

Normalization now has one active job and at most four accepted active/queued requests per server process (including saved galleries/covers); excess requests return recoverable busy feedback. Creation also keeps its process-aware filesystem lock. Browser thumbnails decode one bounded source at a time and retain only small output Blobs; native decoder memory is implementation-dependent, so no exact browser-RAM guarantee is claimed. Header preflight follows the W3C PNG specification, ITU T.81, WebP container/lossless specifications and RFC6386; it assists resource bounds and does not replace browser/Sharp decoding.
