# Optional Telegram OIDC for private beta

Status: backend and invitation/link UI are config-gated and tested with a synthetic signed OIDC provider. **Live Telegram sign-in has not been tested.** No BotFather credentials, DNS, real callback or public endpoint were configured during development. Password login remains available and unchanged.

## Owner prerequisites

1. Complete the separate HTTPS deployment/security gate and own an exact trusted origin such as `https://items.example.com`. Telegram login does not work on a LAN HTTP URL or the default local loopback mode.
2. In the owner's own @BotFather session, create/select the bot and use Login Widget to register both the exact site origin and callback `https://items.example.com/auth/telegram/callback` as Allowed URLs. Obtain the issued Client ID and Client Secret there. [Telegram's official OIDC instructions](https://core.telegram.org/bots/telegram-login) describe this registration and the Authorization Code + PKCE flow. Do not paste the bot token, client secret or invitation tokens into Git or chat.
3. In the private runtime config outside Git, set `ALL_ITEMS_TELEGRAM_CLIENT_ID` and `ALL_ITEMS_TELEGRAM_CLIENT_SECRET` together. `ALL_ITEMS_ORIGIN` must equal the registered HTTPS site origin, and `ALL_ITEMS_PROXY_MODE=https-proxy` must pass preflight. Restart the production app. If either credential is absent, the Telegram controls are hidden and local password sign-in continues.

The app requests only `openid`. It does not request a phone number, profile, chat access, bot messages or file access. The [openid-client](https://github.com/panva/openid-client) library performs discovery, code exchange, PKCE/nonce checks and RS256 JWKS signature verification. The implementation pins Telegram's issuer and endpoints, checks audience, issue/expiry time and subject, and takes identity only from the validated ID token. No userinfo call is made. Login attempts never associate by mutable username/display name.

## Invite and account operations

- On the private local machine, run `npm run auth -- telegram-invite` in an interactive terminal and enter the chosen **new** username. The command prints one random code once, valid for one hour. Deliver it privately to the intended invitee, who opens the HTTPS login page, expands the invitation section, enters the code and continues with Telegram. One successful exchange creates exactly one disabled=false, non-admin account with no inventories and one Telegram identity association in a transaction. A successful Telegram login with an unlinked identity and no invite creates nothing.
- Run `npm run auth -- telegram-invite-revoke` and enter that username to revoke unused invitations. Existing local `invite`, `reset`, `revoke`, `disable` and `revoke-all` remain available. Disabling/revoking a user affects sessions regardless of how they signed in.
- An existing password user opens **Account settings**, enters the current password and chooses **Connect Telegram**. The callback verifies the Telegram subject, then returns to a local continuation page. The user explicitly confirms or cancels the pending link in the **same still-valid session**. A subject already linked to any account cannot be linked again. A password user may disconnect by reentering the current password. Telegram-only users cannot disconnect the last method; local `auth reset` can first add a password and revoke prior sessions.
- After Telegram returns, click **Continue** on the local page. This same-site navigation is intentional: the regular app session cookie is SameSite Strict and is not assumed to accompany a cross-site redirect chain. The link confirmation then appears in Account settings. If Telegram is unavailable, the start form retains the entered invitation/password in the browser and shows a localized retry error; ordinary password sign-in still works.

Flow state and PKCE verifier are installation-local, expire after five minutes and are consumed once before token exchange. Callback requires its HttpOnly Secure Lax flow cookie as well as the database state; linking additionally binds the verified subject to the original session digest. A lost network response can burn a flow: start a fresh one. Invitation codes remain one-use and can be revoked/expired; failed exchanges do not consume them. Start requests have an installation-wide 30-per-15-minute SQLite budget. This is not a distributed anti-abuse service.

## Operator checks before inviting anyone

Use a synthetic installation first. Verify local password login, an invited Telegram-only account with empty inventory, link/cancel/unlink for a password account, duplicate-subject rejection, expired/replayed invitation denial, disable/revoke, media/archive isolation, and a production restart. Then perform a live BotFather callback only after the exact domain/TLS/proxy configuration and independent security review. Do not treat the synthetic signed-provider tests as a live Telegram result.
