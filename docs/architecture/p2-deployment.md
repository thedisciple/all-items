# P2 Windows HTTPS deployment preparation

Status: configuration and synthetic tests only. Do not point a public domain, forward ports, open a firewall, or start a tunnel until the separate security and owner approval gates. This runbook describes the direct-home topology if a reachable permitted home address is verified; a CGNAT relay or managed tunnel needs a separately reviewed configuration.

## Read-only network choice

Compare the router's displayed WAN IPv4 with a separately observed public IPv4 without recording either in Git. A WAN address in RFC1918 or 100.64.0.0/10, or a mismatch, suggests CGNAT or double NAT; a match does not prove inbound reachability. Check IPv6 allocation and inbound firewall independently. Ask SBB whether inbound hosting and a public/static address are available under the actual subscription. Measure upload throughput and note PC sleep, reboot and power reliability. The [SBB technical conditions](https://sbb.rs/wp-content/uploads/2025/10/net-tehnicki-uslovi.pdf) describe multiple IPv4 arrangements, not this installation's allocation.

If public reachability and ISP permission are confirmed, prefer owned DNS plus Caddy on the Windows host and narrowly forwarded 80/443. If CGNAT persists, compare a self-managed VPS terminating HTTPS over a restricted WireGuard backhaul (SQLite/media remain on the PC, VPS sees terminated traffic) with a managed tunnel's vendor dependency. Neither bypasses application authentication. Choose only after costs, privacy and availability are reviewed.

## Private production preparation

1. Stop writers. Verify an installation backup and run its isolated drill using `npm run backup -- create` and `npm run backup -- drill UUID` with the **intended** private `ALL_ITEMS_DATA_DIR`. Preserve the verified copy. For a new test installation, use synthetic accounts/data and a new directory outside Git.
2. Use a dedicated non-admin Windows service identity with read/write access only to the private app data and its private configuration; grant Caddy only its own config/cert storage and the proxy secret. Deny ordinary users access to DB, media, backups and config. Keep the repository/build read-only to the service where practical. Never place secrets in system-wide environment variables, logs, shell history or Git.
3. `npm ci`, `npm run typecheck`, `npm run lint`, `npm test`, `npm run build` in a versioned checkout. Build does not migrate configured data. Copy `deploy/runtime.env.example` to an access-restricted path **outside this repository** and fill exact `ALL_ITEMS_DOMAIN`, `ALL_ITEMS_ORIGIN`, `ALL_ITEMS_PROXY_MODE`, 32 random bytes base64url for `ALL_ITEMS_PROXY_SECRET`, and an existing absolute local Windows `ALL_ITEMS_DATA_DIR`. Generate the secret locally with a cryptographic random source. The same secret must be supplied privately to Caddy. Optional Telegram Client ID/Secret belong only in the app's private runtime config after [BotFather registration](p2-telegram.md); do not give the Telegram secret to Caddy.
4. `powershell -NoProfile -File scripts/start-production.ps1 -ConfigPath C:\private\runtime.env -ValidateOnly` performs a no-migration preflight. Without `-ValidateOnly` it starts the production server at `127.0.0.1:3000` and applies any pending migration. Inspect the service identity, private path and verified backup first. `npm run dev` is never the network deployment.
5. Copy `deploy/Caddyfile.example` and `deploy/caddy.env.example` to separate access-restricted private paths, replace the exact domain and the **same** proxy secret used by the app. The Caddy env file contains only domain and proxy secret, never Telegram credentials. Run `caddy fmt --overwrite Caddyfile` and `caddy validate --config Caddyfile --envfile caddy.env` before a controlled service start. Caddy terminates and renews HTTPS, pins upstream Host/scheme, strips `Forwarded`, caps request bodies and forwards only to loopback. Do not expose the Caddy admin API or backend port. Keep Caddy's `XDG_DATA_HOME` and `XDG_CONFIG_HOME` directories persistent and restricted so certificates and configuration survive reboots. Follow [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https), [file locations](https://caddyserver.com/docs/conventions) and [Next self-hosting](https://nextjs.org/docs/app/guides/self-hosting).
6. For a reproducible Windows service path, obtain a vetted [WinSW 3 binary](https://github.com/winsw/winsw) and copy `deploy/AllItems.App.xml.example` and `deploy/AllItems.Caddy.xml.example` outside Git. Replace placeholder absolute paths; create the private log/certificate directories and grant only the respective dedicated service accounts access. The examples start as **Manual** and prompt interactively for the service account during installation, so no OS password belongs in XML or command history. In an elevated local terminal, use `winsw install C:\private\AllItems.App.xml` and `winsw install C:\private\AllItems.Caddy.xml`; inspect the installed services before starting them. Only after the separate deployment approval, set their startup type to Automatic, start the app and then Caddy, and verify a cold reboot, restart-on-failure and certificate renewal. Do not run these install/start commands as part of tests. [WinSW configuration](https://github.com/winsw/winsw/blob/v3/docs/xml-config-file.md) documents the account prompt, manual start and failure restart; [Caddy's Windows service guide](https://caddyserver.com/docs/running) documents supervised `caddy run`.
7. Keep service stdout/stderr private with size rotation; record availability, error class and duration only, never inventory payloads, image bytes, passwords, session cookies or proxy secrets. Monitor a synthetic unauthenticated 403/redirect response and certificate expiry from outside, plus service exit/restart and disk space; notify the operator privately. Do not use actual inventory or account content as a health probe.
8. Schedule verified installation backups and periodic isolated restore drills. Store an encrypted/off-machine copy under an owner-chosen retention policy; confirm recovery of synthetic data first. Preserve migration backups, pinned and partial copies. Review [local backup operations](local-backups.md). A rollback restores a verified prior copy into a separate directory under the matching application version; never reverse SQL or overwrite the running installation.

Updates require a fresh verified backup/drill, a built and tested versioned checkout, a brief writer stop, migration preflight, health check and rollback window. Never run two app versions as concurrent writers against one SQLite installation. The owner must separately register the exact HTTPS origin and Telegram callback with BotFather before live OIDC can be enabled.
