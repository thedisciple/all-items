# Bounded experiments after M4C

Research checked 2026-11-13. These are implementation-ready follow-up tasks, not shipped runtime features. Mobile beta acceptance takes precedence.

## Autoresearch method

[Karpathy's autoresearch](https://github.com/karpathy/autoresearch) uses controlled, repeatable experiments with a fixed evaluation budget. All Items adopts the hypothesis/baseline/change/measure/keep-or-reject method, not the training stack or its GPU requirements.

First task: compare inventory search/filter query alternatives on deterministic 1,000 and 10,000 synthetic rows, equal timestamps, category/stock/collection distributions, and multiple synthetic owners. Use the existing libSQL/Vitest infrastructure. Freeze expected ordered IDs, filtered counts, authorization failures and page boundaries before experiments. Correctness must be identical. Measure warm median/p95 across 20 repetitions after three warmups; record cold timing separately, Node/SQLite versions, machine and query plan. Reject any correctness/security regression or >10% p95 regression in another measured query. Keep a candidate only with >=15% median improvement on the stated bottleneck.

Run in a new branch/worktree, never the live checkout. Maximum five single-change experiments, 30 minutes wall time, one local worker, 256 MB generated data, 10,000 generated items, 20,000 model tokens, no paid APIs, credentials, production data or active deployments. Stop at any bound. Do not change acceptance tests to improve a score. Record hypothesis, baseline, diff, inputs, command, results and decision in an experiment log; delete only that run's verified temporary directory. No automatic merges. Ollama/Qwen/RTX A4000 are optional future resources. M4C's focused pagination measurements are validation, not an autonomous experiment engine.

## WebMCP architecture task

Current primary sources: [Chrome overview](https://developer.chrome.com/docs/modern-web-guidance/guides/webmcp/webmcp) and [agentic JavaScript tools](https://developer.chrome.com/docs/modern-web-guidance/guides/webmcp/agentic-javascript-tools). The documented API is **document.modelContext**, not navigator.modelContext. Early preview requires a compatible Chromium build (documented minimum 146.0.7672.0) and `#enable-webmcp-testing`, or the documented opt-in trial. This does not establish Safari, Yandex Browser, Edge or Codex consumer support. No flags, trial tokens, packages or registrations were enabled in M4C.

Future prototype: feature-detect in an authenticated inventory-scoped client adapter. Follow the current documented React lifecycle approach (`useWebMCP` from `use-webmcp-tool`) after reviewing that dependency, or keep registration in a separately owned lifecycle adapter; do not register during rendering. Registration uses AbortSignal cleanup; there is no assumed unregisterTool. Abort registration does not cancel already executing calls: validate scope and cancellation again for every execution.

Start with at most two tools: `search_items` (query <=160 chars, page size <=25, bounded selected fields, no notes/private sale fields) and `get_inventory_stats` (counts only). Arguments are Zod validated. Inventory UUID is never authorization. Reuse authenticated secured server reads with exact origin/session checks and explicit ownership; every execution must reauthorize, including after account/inventory changes. Return semantic errors. Declare readOnlyHint; treat it as a hint, not a security boundary. Do not expose admin, filesystem, backups, secrets, writes or destructive tools. `get_item_details` needs a deliberately reviewed field allowlist; defer `find_low_stock` until thresholds have defined semantics.

Verification procedure: isolated synthetic installation, compatible Chrome profile, enable the testing flag and restart; inspect `document.modelContext` in DevTools, inspect registered tool schemas with the documented test API, execute valid/invalid/bounded inputs, switch inventories/accounts, expire session, and verify no foreign IDs appear. Inspect network requests and compare normal secured reads. Verify registration cleanup and in-flight execution behavior. Disable the flag/API and confirm the entire normal application still works. Test API execution is not proof an external agent consumer can discover/use tools. Never run this procedure on the active beta installation. No parallel MCP server is needed. Delivery gate requires ordinary UX/security/physical-device acceptance first.
