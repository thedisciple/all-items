# Product opportunity register

M2D-R2 interaction rules are governed by the [design manifesto](design-manifesto.md). The planned multi-photo foundation is an additive M3 media migration and gallery, preserving existing asset IDs and primary images; it is not implemented by R2. The M3 archive must serialize a list of media assets per item.

This register retains prioritized proposals. Status vocabulary: idea, research, planned, implementing, implemented, rejected. Complexity: low, medium, high. Research evidence and inferences are separated in [design references](design-references.md). No future item below is implemented unless explicitly marked.

## Planned architecture boundaries and pilot

Archive export and empty-workspace import are implemented in M3.2. Other integrations below remain plans.

- **Archive service:** revision 3 portable ZIP with a revision 2 recovery adapter, JSON manifest/payload, checksums, readable relative paths, distinct CSV export, validated preview, empty-workspace staged restore and integrity checks are implemented. Populated-workspace conflicts, backup-before-replacement, optional encryption, and styled XLSX remain planned. Never use a raw SQLite dump or absolute machine paths as the portable format.
- **Adapters (future):** media/blob storage, optional backup destination, AI provider (including possible Ollama or OpenAI), external authentication identity providers, and MCP/API. Local storage stays the default; S3-compatible and WebDAV/Nextcloud are possible destinations, not commitments.
- **Telegram boundary:** possible Telegram Login/OIDC identity mapping, Mini App UI, or user-initiated sharing are separate from inventory storage. Telegram is not the primary DB/media backend. Do not request MTProto session credentials. Telegram's [Bot Developer Terms](https://telegram.org/tos/bot-developers) restrict standalone cloud-storage services and disclaim guaranteed availability/integrity of cloud-stored data; this makes Bot Platform storage unsuitable as the archive or backup foundation. See [Telegram Login](https://core.telegram.org/bots/telegram-login).
- **Private beta (M3.5):** plan 5–10 invited testers only after production-mode HTTPS, invite-only onboarding, secure sessions, workspace authorization on every service and media route, CSRF/origin protection, rate limits, upload limits, security headers, tested backup/recovery, safe owner-data migration, and privacy-conscious feedback. Keep development endpoints private. Optional Telegram OIDC must map identity only and retain a local-login fallback.
