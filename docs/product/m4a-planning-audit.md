# M4A planning audit

Starting HEAD: 34f26b0f984039b02aef187d8f02f428577202d1. Scope: a read-through of the complete roadmap, opportunity register, marketplace/gamification concepts, architecture and accepted/proposed ADRs against current services and M3.4 validation. This is a planning consistency audit, not a new security certification or commitment to implement every proposal.

## Findings and additions to the supplied brief

1. **Delivery order:** the old M3.5 pilot label appears after an unstarted M4 and must not imply a permission or dependency shortcut. M4A is the current UX/creation task. M4B recovery/restore drills and usability checks follow. Human-reviewed AI identification is a separate next capability; authenticated hosting/shared accounts require their own later security gate. Optional personal organization, themes, integrations and marketplace remain proposals.
2. **Status drift:** the register still calls implemented Add Item recovery an idea, describes revision 3 as current, and proposes photo order despite M3.4 implementing it. ADR 0005's source/language decisions are historical; ADR 0006's archive half is implemented, its beta half is not. Mark supersession explicitly and keep historical rationale. Separate completed readable archive paths from still-proposed flexible attributes and list/grid views. Category chips are actionable independent filters in current lists; an old principle says non-interactive.
3. **Ambiguous creation acknowledgement:** a retry after the final server commit but before its response must not create a duplicate item or consume another human number. Add a durable inventory-scoped operation identity and receipt, check retries and changed payloads, and recover ambiguous outcomes before cleanup. This is a substantive addition to C2/D11. No hidden provisional items.
4. **Resource budgets:** ten source/derivative pairs cannot be sent through the existing 22 MiB action body as one request. Keep per-photo requests bounded and process sequentially, with a separate total creation budget and bounded private staging lifetime. Preserve pending crop inputs in the browser; do not stage unprocessed raw metadata. Cover failed/expired staging and cross-inventory token substitution.
5. **Draft upgrades:** shape versioning must preserve original revision/CAS identity; reading a legacy draft must not silently rewrite another tab's revision. Keep limits across all inventory drafts and validate schema, total bytes and primary/order references.
6. **Compatibility:** the ten-photo addition policy is not a persistence/archive constraint. Rev 6 remains current and historical >10 galleries stay intact. Cap checks must run inside the same write transaction as additions, including concurrent clients. Reorder staleness/failure rolls back local order and never rewrites primary/cover UUIDs.
7. **Evidence:** separate CSS viewport/zoom simulation and touch/camera mocks from physical hardware. State the browser's touch gesture constraints and verify real pointer traces; library names or configured timers alone do not prove the drag works.

## Design choices for checkpoint A

Keep the existing intrinsic persistent filters; a shared wrapping toolbar makes Add Item and Search peers without adding disclosure clicks. The minimum search basis is 15rem; controls wrap when the available region is genuinely exhausted. A header-owned toggle retains a fixed 44px target and vertical center independent of sidebar content; mobile navigation remains labelled and always available. Dialog action insets share a spacing token including safe-area padding. Visible currency options use ISO codes, with translated names retained as accessible context. These are task hypotheses checked against synthetic implemented geometry, not a copied MoneyRS layout.

## Future dependency order

Reliable local recovery/restore drills and measured usability precede a release/pilot claim. Optional AI identification uses reviewable proposals, provider adapters and explicit local/cloud consent; original marking remains authoritative. Accounts/roles and authenticated HTTPS are required before sharing/network access. Cross-inventory projects keep composite references and revocation/privacy semantics; listings remain a separate explicitly public representation; stock reservations, legal/payment/operator decisions precede commerce. E2EE synchronization is a separate threat-model decision, not an automatic consequence of accounts. Goals/achievements remain optional and non-manipulative.
